# 筛选、证据与数据契约

## 机会判断

按以下优先级进行定性比较，逐项给出依据和未知，不输出没有依据的精确总分：

1. **客户可触达性**：具体角色、公开社区/目录/搜索需求、可执行的接触途径。泛称“做 SEO”或“发社交媒体”不够；区分对手已证明渠道和你待验证的渠道。
2. **付费需求**：重复发生的任务、时间/损失/现有支出、实际付款或迁移迹象。点赞、报价、未经证实的市场规模不能替代。
3. **开发与维护**：用默认资源估算窄切口 MVP 的工时范围、依赖、支持工作、数据和运行成本。可做出界面不等于能稳定交付。
4. **差异化**：针对哪个客户、流程或集成改善什么；要与现有竞品比较，不能只写“更便宜”或“加 AI”。
5. **持续收费**：使用频率、持续价值、取消理由、季节性和一次性需求。

报告中将 `commercial`（有具体商业信号）、`demand`（有需求信号但商业未验证）、`insufficient`（证据不足）分组，组内按上述优先级排列。分组表示证据类型，不自动决定机会优劣；公司披露、客户自述等局限仍要写明。`shortlist` 表示值得优先验证；`watch` 表示待补证据；`exclude` 必须说明不符合哪条约束。未知人数不单独淘汰。

## 深挖交付

- **竞品**：现有产品、直接竞品与人工/表格替代，比较客户、工作流、价格和切换成本；每个外部事实给来源。
- **MVP**：只解决一个客户群的一个工作闭环，列首个可收费范围、明确不做的能力、依赖、4–6 周工时假设与维护负担。用户资源变化时重新估算。
- **成本**：开发工时、月固定费用、单位调用/任务成本、低/中/高用量情景。报价附来源，估算标记假设；毛利假设与收入事实分开。包含 AI 调用、平台费用、存储、邮件、支持等实际相关项。
- **验证计划**：假设、目标受访者、公开获客渠道、英语文字邀约/问题草稿、时间与预算、成功与停止阈值、失败后下一步。阈值是预先拟定的实验标准，不冒充行业统计。输出草稿不代表已发送；用户授权实施后再使用相应工具。

## JSON 契约（schema_version 1）

脚本只验证结构、引用完整性、日期和重复身份，不能证明网页真实性、收入可信度或商业判断正确。`fact` 表示来源支持的陈述，不意味着第三方已独立审计。

根对象字段：

| 字段 | 约定 |
| --- | --- |
| `schema_version` | 整数 1 |
| `mode` | `discovery` / `deep-dive` / `smoke-test` |
| `observed_on` | 用户时区研究日期，YYYY-MM-DD |
| `scope` | 客户、市场、资源、特殊要求、执行范围摘要 |
| `shortlist_limit` | 非负整数，默认 5，用户明确要求可改 |
| `queries` | 实际执行的搜索字符串数组；无网络时可空并说明 |
| `limitations` | 范围、访问失败、未确认事项与停止原因的字符串数组 |
| `sources` | 来源对象数组，包含失败访问；失败来源不能作为事实引文 |
| `products` | 去重候选数组，按推荐顺序排列，保留观察/淘汰理由 |

每个 source：`id`（本次唯一字符串）、`url`（公开 HTTP(S) URL）、`title`、`kind`（`official` / `founder` / `customer` / `directory` / `third_party`）、`status`（`ok` / `blocked` / `error`）、`accessed_on`、`published_on`（日期或 null）。URL 保留证据定位需要的路径及参数，移除追踪参数和凭据；部分正文未读到时不要用它支持对应事实。

每个 product：

- `name`、`website`：产品名称与核实的规范官网 URL。生态产品保留产品路径或产品 ID 查询参数，不合并同平台不同应用。
- `decision`：`shortlist` / `watch` / `exclude`；`reason`：具体取舍理由。
- `evidence_level`：`commercial` / `demand` / `insufficient`。
- `claims`：必须包含下面全部字段，每个值是 claim 对象；尚未知的信息也保留键。
- `revenue`：单独收入对象，见下文。
- `analysis`：深挖时必须包含 `competitors`、`mvp`、`costs`、`validation_plan`，每个值也是 claim；发现模式可省略。

`claims` 的字段：`customer`（使用者/付费者）、`problem`、`pricing`、`team`、`demand`、`acquisition`、`wedge`、`effort`、`recurrence`、`risks`、`next_step`。多个来源支持一项长分析时，在文本中说明哪个来源支持哪项事实，不以末尾一串链接替代对应关系。

claim 的三种合法形式：

```json
{"text": "官网 Pro 计划报价 USD 19/年；这不证明存在付费客户。", "basis": "fact", "source_ids": ["pricing"]}
```

```json
{"text": "推断：可面向小型代理机构验证批量交付需求；渠道尚未验证。", "basis": "inference", "source_ids": []}
```

```json
{"text": null, "basis": "unknown", "source_ids": []}
```

上述金额只是格式示例。`fact` 必须至少引用一个已成功访问的来源；`inference` 可无来源，但要写清假设、估算依据和验证办法；`unknown` 固定为 null 和空引用。推荐产品必须有具体 `demand` 来源；仅有定价页即使结构校验通过，也不满足研究入选条件。

收入对象：

```json
{"status": "unknown", "text": null, "as_of": null, "source_ids": []}
```

可用状态：`unknown` / `founder_reported` / `verified_record`。后两者必须提供 `text`（金额、币种、MRR/ARR/累计收入等原始口径）、`as_of`（数据所属时期，不用访问日期代替）和来源。`verified_record` 仅用于实际看到可追溯经营记录并核对其范围，仍说明验证机制与局限；创始人文章/截图默认 `founder_reported`，不等于审计收入。只知道报价时收入保持 unknown；时期不明的数字留在风险说明，不作为可用收入。

## 去重与历史

脚本将 HTTP/HTTPS、www 前缀、末尾斜杠及常见追踪参数差异视为同一身份；保留产品路径和业务查询参数。同一轮发现重复时拒绝保存，先人工合并证据并处理矛盾，不静默保留最后一条。

`--history` 可多次指定历史 results.json；按观察日期排序，同一天按参数顺序由后者代表更新观察。对每个产品取最近一次记录，比较事实、判断与来源 URL，忽略来源 ID 更名。输出 `new`、`returning`（附变化字段）和 `not_rechecked`。后者仅表示本次没查，不表示停运、被淘汰或失去价值。品牌改名、并购、多域名同产品须由 agent 核实并在输入中统一；脚本不做模糊合并。

保存生成 `results.json`（完整证据）、`changes.json`（比较结果）及 `report.md`（人类阅读报告）。已有目录拒绝覆盖。写入中断可能留下不完整新目录；换新运行目录重试，旧快照保持不变。
